# Diagram layout and routing rulebook

## Layout setting

Enterprise and flowchart diagrams default to `grid`. Diagram frontmatter may set `config.layout` to `grid` or `open`. An unknown value gives one warning and uses `grid`. The command-line option `--layout grid|open` sets the run default; the diagram's own setting takes precedence.

`grid` uses the shared grid and placement rules below. `grid` includes the compaction step in rule 2.11. `open` skips shared-grid placement and permits free node and group positions. Both modes use the same routing, ports, straight runs, rounded corners and crossing rules. Boxes and unrelated group frames must not overlap in either mode.

## Legend setting

Diagram frontmatter may set `config.legend` to `off`, `on`, `bottom-right`, `bottom-left`, `top-right`, `top-left`, `below`, `right`, `table`, or a placement hint such as `right-of id`. It defaults to `off`; `on` means `bottom-right`. The command-line option `--legend` sets the run default and diagram frontmatter wins. An image legend is placed after the main layout and never changes its nodes, routes, labels or score. It contains only the distinct visible node and line types used by the diagram, in first-use order; invisible connectors are omitted. It sits outside the main bounds with one grid step of clearance. `table` draws no image legend and adds a two-column Symbol/Type table after the diagram. Main-layout legality and quality checks exclude legend samples; the legend may not overlap itself or the main diagram.

> **Consolidated decisions (14 Oct 2026).** The operative rules below incorporate these decisions; this note is a history summary, not a separate precedence layer.

> 1. Offset child in the next rank: use one corner into the target, entering as rule 4.11 sets, as rule 4.8 says.

> 2. Diamond branches require 50 px before the first corner. Other source runs require at least the 20 px corner radius; terminal runs require at least the arrowhead length. A base rank gap remains 2 grid steps.

> 3. A gap grows by a whole grid step when it runs out of tracks.

> 4. A node that rejoins the main path stays on the main path.

> 5. Ties: branches go left of the main path, return tracks go right, diamond branches use symmetric edge ports, label clearance is the width of "n", and frame padding is 1 grid step.

> 6. The "Arrangement kept" check of brief section 9 allows the reordering in section 2 of this rulebook.

## Terms

- **Grid step**: 30 px. This is the fine drawing grid for frame edges, tracks and gap growth. Nodes and linked groups are placed and moved by whole logical cells (term Grid, rule 1.2). Ports, arrowheads, rounded-corner geometry and text bounds are continuous drawing coordinates and may be fractional.

- **Grid**: the logical placement grid of a `grid`-mode diagram: one shared set of columns and rows of **base cells**, with a column gap between neighbouring columns and a rank gap between neighbouring rows. Every base cell has the same base cell width and base cell height (1.3). A cell is a unit of occupancy, not a drawn border. A rectangular node's **occupied region** is one contiguous rectangle of whole cells, given by its start row, start column, row span and column span; both spans are positive integers. The node's rendered rectangle is its whole occupied region, including the gaps between its own cells. The gaps round the region separate it from other nodes and follow the spacing rules. Column gaps and rank gaps need not be equal, and a gap may grow by whole grid steps for routing, labels and frames (1.5, 1.7, 7.3); growth changes the gap, never the base cell dimensions. A node that spans a grown gap includes the grown gap. In `open` mode, the logical grid does not apply. A span has no maximum. A node's region is never L-shaped, never skips a row or column and never consists of separate cells. A node that spans several cells is still one node, with one id, label, shape, set of relationships, group membership and set of hints, and one continuous connection boundary (term Node geometry); spanning creates no extra nodes, relationships or ports. The node reserves every cell of its region, and occupancy is read only from regions, never from node positions or midpoints. There are no local grids, per-node pixel offsets or per-cell distortions. The base cell width and height are configured parameters (1.3), set before any label is fitted and fixed for the whole layout. An **internal gap** lies between cells of the same node; an **external gap** separates different occupied regions.

- **Rank**: a node's row in flow order. Mermaid's ranking gives the starting rank. A line is **forward** when its target is in a later rank.

- **Gap**: the clear space between two neighbouring rows of cells (rank gap) or columns of cells (column gap). A gap inside a node's occupied region is part of that node; a gap between separate nodes keeps them apart. Base rank gap: 2 grid steps, providing a default routing corridor for 20 px rounded corners, arrowhead clearance and independently allocated tracks; it is not derived from a universal 50 px straight-run requirement. Base column gap: 1 grid step.

- **Track**: a line inside a gap, parallel to the gap, on which a straight run travels. Tracks follow the coordinates of the ports they serve (3.2). Every track is at least line_spacing (15 px) from every other track and from each node outline or frame edge bounding the gap, so a gap of width W holds at most floor(W / line_spacing) - 1 tracks: a 30 px gap holds one track, on its centre line, and a 60 px gap holds three. This is the geometric maximum. A track that a line turns onto from a port on a bounding outline must also leave that line's 4.4 run and corner_radius clear, so forecasts (1.7, 5.1) count only tracks that satisfy 4.4 for the lines they will carry; n forecast tracks need a gap of at least (n + 1) x line_spacing, and a track that a line turns onto from a port on a bounding outline lies at least min_straight_run from that outline, and at least corner_radius, plus arrowhead_length_px for an arrowheaded line, from an outline the line turns into (4.4). **Shared track**: two parallel segments of different lines share a track when their extents overlap along their direction by more than geometry_tolerance_px and their perpendicular distance is less than line_spacing minus geometry_tolerance_px. Segments of the same line, and segments that only meet at a crossing point, are exempt. Sharing a track is a legality fault (5.1, section 10).

- **Port**: the point where one line meets a node outline. Box and diamond edges each accept any number of distinct ports, distributed symmetrically at k/(n+1) along the edge (3.2); a single line uses the edge centre. Diamond vertices are the four tips, not mandatory branch ports. Every port lies exactly on the node's connection boundary (term Node geometry).

- **Sides**: the **upstream side** faces earlier ranks (top); the **downstream side** faces later ranks (bottom). The **side that faces the target** (on a source) or **the side that faces the source** (on a target) is whichever of top, bottom, left or right faces the other end; the **far side** is the opposite side. A side or port is **free** when no line uses it.

- **Straight run**: a straight segment. Ordinary runs are horizontal or vertical; the initial run leaving or entering a sloped diamond edge is the sole exception and follows the edge normal (3.1). Diamond branches travel at least 50 px along that normal before turning onto the grid; other lines require a port-to-vertex distance of at least min_straight_run (20 px) before a corner, measured from the port to the corner's vertex (where the centre lines of the two runs meet), so a corner_radius arc may begin at the port, and an arrowhead-length terminal run. A straight line with no corner needs no artificial source-side clearance.

- **Corner**: normally a quarter-circle of radius 20 px joining two orthogonal straight runs at a right angle. A diamond-edge-normal run turning onto the grid uses a tangent transition for its actual change of direction, with the same 20 px minimum bend radius; it need not be a quarter-circle. An **elbow** has 1 corner. A **Z** has 2 corners, and its first and last runs point the same way.

- **Main path**: see rule 2.18.

- **Branch**: a path that leaves a main-path node and is not on the main path. A **detour** rejoins the main path at the next main-path node. An **early exit** ends, or rejoins the main path further on. A **loop branch** ends in a back edge.

- **Back edge**: a line whose target is in an earlier rank than its source. Its **return track** is the track it runs on, outside every node it passes.

- **Fan**: 2 or more lines on one side of one node that go to, or come from, nodes in one rank.

- **Group / frame**: a group is a Mermaid subgraph; its frame is the rectangle drawn round its members. Every frame has a title strip at the top and 1 grid step of padding on each side.

- **Label gap**: the width of the letter "n" in the label font. It is the clear space between a label's text and its line on each side.

- **Main link**: the line to or from the node's one parent, or its first declared incoming line when it has several.

- **Strongest flow** (the longest decision-free run): the flow with the most nodes from its start, or from the last decision, to the converging node; the first declared wins a tie.

- **Cluster**: see rule 2.20.

- **Peer**: an element, note or group at the required nesting level in the same group; see rule 2.21(c).

- **Honoured**: the final placement or route geometry satisfies the retained hint; horizontal and vertical placement axes are honoured or dropped independently; see rule 2.21.

- **Note**: a free-text box with a dog-ear corner; see rule 2.22. A **plain connection** is an undirected line to or from a note; see rule 4.10.

- **Nearest free cell**: the free cell region of the required spans with the fewest grid steps from the target region, trying the same rank first, then earlier ranks, then left before right.

- **Forced minimum**: see rule 2.13.

- **Wrapped**: cut into rows or columns by rule 2.12.

- **Node geometry**: every node has three geometries. **Visual bounds** are the complete visible extent of the rendered node, including decorative overhangs and projections. The **connection boundary** is the shape-specific boundary on which ports may be placed; it may differ from the outermost visible outline and may consist of several edges or segments. **Obstacle geometry** is the complete occupied geometry of the node, including decorative overhangs and projections, which unrelated lines and nodes must not intersect. For an ordinary rectangular node all three coincide. For a node with decorative features, the connection boundary may follow the main body rather than those features. Every connection ends exactly at its allocated port on the connection boundary. A line may approach its own node only along the permitted approach to that port and never passes through the node's occupied geometry. Decorative features give no extra ports unless the shape defines them as eligible. The shape renderer supplies all three geometries as part of its contract, and the router uses them without shape-specific logic. Until a shape supplies its own definitions, all three default to its rectangle, which is the current behaviour. Collision detection uses the actual obstacle geometry where it is available, rather than treating the bounding rectangle as solid. Example: a contract shape's rectangular body is its connection boundary, and its top overhang is visual bounds and obstacle geometry only. A line from the right ends at the body's right edge, not at the overhang's rightmost point, and unrelated lines may not cross the overhang. For the wavy-bottom representation shape, the bottom connection boundary follows the wave's midline; an arrowhead tip may touch the wave but never crosses it.

Every rule is generic: it uses structure and geometry, never labels, samples, tests or group titles; only hints identify peers by id (2.21). **Precedence has four distinct levels:** (1) hard legality, including geometry and section 10; (2) honoured hints, which override automatic placement and eligible routing faults; (3) fewer routing faults, counting only faults not explicitly permitted by hints; (4) scored optimisation. A hint cannot override hard legality, but can override automatic placement, cluster membership preferences and eligible routing faults. Rules are expressed for top-to-bottom (TB); rule 1.1 maps them to other directions. `webshop-target-rules.md` retains historical pictures and decisions.

## 1. Grid and spacing

1.1 For LR, read left for top, right for bottom, top for left and bottom for right. BT and RL mirror TB and LR.

1.2 In `grid` mode, place every rectangular node on the one shared logical grid (term Grid). A node's placement is its start row, start column, row span and column span, and its position and dimensions follow from that occupied region alone; a node's geometric centre is derived from its drawn shape for drawing and measurement only and never decides placement. The region is one contiguous rectangle of whole cells; spans are positive integers with no maximum, and fractional occupancy is not allowed. No cell belongs to more than one node. A node grows by taking further whole columns or rows, to the right, left, down, up or along both axes, whichever gives the best legal arrangement under the precedence and score; right and down are only the final tie-break. Growing one node never changes the size of another. Move nodes and linked groups only by whole cells. Before moving anything, use free contiguous cells if the node can take them without breaking legality or an honoured hint. Otherwise move the affected neighbours by whole cells, keeping their relative order unless a higher-priority rule or honoured hint requires otherwise, keeping every external clearance, and never resizing them; do not move unaffected nodes. Remove genuinely empty rows or columns without consuming routing clearance or any cell a node occupies. The fine grid remains for outward-rounded frame edges, tracks and gap growth. Ports, curves, labels and arrowheads remain continuous drawing coordinates. Placement is deterministic. In `open` mode, the logical grid and cell spans do not apply.

1.3 Base cells. In `grid` mode the base cell width and height (parameters base_cell_width and base_cell_height) are set before any label is fitted, from the renderer's standard rectangular-node size and measured font metrics. The height holds at least two lines of node text plus vertical padding; the width meets the configured minimum plus horizontal padding. Both may be rounded up to whole grid steps and then stay fixed for the diagram. They are never derived from the longest label, the largest or busiest node, label statistics, the node count or a group's size, and are never enlarged because one node needs more room. Node size. A rectangular node fills its whole occupied region as one continuous shape: its width is its column span times the base cell width plus the internal column gaps it spans, and its height is its row span times the base cell height plus the internal rank gaps it spans, each gap at its current size. Node sizes are measured on visual bounds (term Node geometry). Fitting text. Measure each label with the rendering font, size, line spacing and padding, keep explicit line breaks, break at word boundaries, and split a word only when it cannot fit any candidate width; never clip, truncate, overlap or shrink text. Try 1x1 first, with wrapping. If the label does not fit, generate a finite, deterministic set of candidate spans (for example 2x1, 1x2, 2x2) from measured word widths, line breaks, line heights, padding and the size of whole-cell spans, considering width and height independently; leave out a candidate larger in both directions than another that fits, unless other required geometry needs it. Port capacity on the connection boundary at the minimum separation (3.2), departure and arrival geometry, and other mandatory geometry can raise the minimum span. The number of neighbours alone never makes a node grow. Choose among the legal candidates by the placement rules and score (2.13); no candidate is preferred merely for being wider or larger, and a node is never enlarged only to lower the empty-space score. There is no maximum span and no in-between size. Order. Set base cells, measure labels, choose wrapping and span candidates, add port and shape needs, place nodes, allocate ports, route, then validate and score complete candidates and repair (1.7). When any earlier decision changes, recalculate everything that depends on it; no port or route may use stale sizes. Diamonds. A diamond has the base cell width and twice the base cell height. It may grow by whole grid steps, keeping its proportions, when text, port separation, connection geometry or mandatory clearance requires it, and never just to fill its region. It reserves the smallest whole-cell rectangle that holds its visible shape and is drawn centred in it without filling it. No other node may use those cells, but the empty space between the diamond and its region is not part of the diamond; its connection boundary and obstacle geometry come from its drawn shape. Its departure and arrival clearance (3.7, 3.8, 4.4) is checked against neighbouring obstacle geometry, because reserving its cells does not guarantee it. Notes are sized separately (2.22).

1.4 Move nodes by whole cells, and grow gaps only in whole grid steps, across the whole rank or column. Never shrink a corner, straight run, label gap or padding to make something fit (see rank-gap-markup-2.png). Adding a column to a node's span adds one base cell width plus the column gap it spans; adding a row adds one base cell height plus the rank gap. Growing a gap by fine grid steps is a separate operation and never changes a span.

1.5 Make every rank gap equal to the base rank gap of 2 grid steps, and every column gap equal to the base column gap of 1 grid step. This value provides a default corridor for rounded corners, arrowhead clearance and independently allocated tracks; it is not intended to satisfy the longer diamond straight-run minimum. A rank or column gap grows only to hold a label, a Z, extra tracks, required run/corner clearance or a frame, and that growth changes no other gap (see rank-gap-markup.png). These are external gaps between separate nodes; a gap inside a node's occupied region is part of that node (term Grid) and is not counted as clearance.

1.6 Snap Mermaid's positions to the logical grid one whole rank or column at a time, giving each node a whole-cell occupied region (1.2). If two regions would share a cell, move the second node on by whole cells in rank order, and repeat until no cell is shared. Snapping and collision checks use each node's full occupied region, not a single point.

1.7 During initial band placement, size each routing gap from the forecast lines passing through it plus corridor_capacity_buffer. Reserve ceil(forecast x (1 + corridor_capacity_buffer)) tracks, and at least forecast + 1, when the forecast exceeds one line; reserve exactly one track when it is one line, and none when it is zero. Count only tracks usable under 4.4 for the lines they will carry (term Track); a track that a line turns onto from a port on a bounding outline lies at least min_straight_run from that outline, and at least corner_radius, plus arrowhead_length_px for an arrowheaded line, from an outline the line turns into. Space tracks at least line_spacing (15 px) apart and from bounding outlines (term Track), grow gaps in whole steps of track_spacing, keeping band membership, band order and column order fixed; this initial sizing does not change any 5.10 search budget. Repair geometric shortfalls monotonically. First measure the actual shortfall: missing label room calls for wrapping or a larger span (1.3); missing port capacity for a larger span or legal port reassignment; missing track capacity for routing space in a gap; an occupancy conflict for moving nodes by whole cells; missing group room for a larger frame. There is no fixed order among these repairs. Build the complete legal candidates that address the shortfall, and keep the one with the lowest score (2.13), using the existing tie-breaks (9.5) and then a deterministic final choice. When growing an external gap and growing an internal gap would both meet the need legally, grow the external gap; a grown internal gap enlarges every node that spans it and adds no routing corridor there. Every repair keeps whole-cell occupancy, non-overlap, external clearance, honoured hints, group membership, mandatory routing geometry and the main-path movement limits. Accept a repair only when it strictly reduces the measured shortfall or its fault count, or meets the strictly improving candidate rule (2.14); a repair that lowers the fault count in the fault-first order of 9.1 is accepted even if its score, crossings or bends rise, and no repair may raise the legality-fault or routing-fault count; never retry an unchanged state or grow without limit. After a gap changes, update cell positions, sizes of nodes spanning it, visual and obstacle geometry, frames, ports, routes, legality and score. A shortfall caused by a port away from the middle of its edge and insufficient corner clearance is repaired by moving the unhinted child to a different column, not by growing the rank gap. Clearances, spacing and inserted space are measured on visual bounds (term Node geometry). If no legal repair exists, draw the visibly marked fallback of rule 5.7 and issue a diagnostic; never omit the diagram.

1.8 Hard: every flowchart begins at the top of the page (the start node at diagram N). The main flow comprising normal sequence edges and Yes branches runs downward in top-to-bottom diagrams; rule 1.1 maps this start and downward main flow for other declared directions. When two legal placements tie on score and routing quality, keep the earlier node farther left; when horizontal position also ties, keep it higher.

## 2. Placement

2.1 Start from Mermaid's ranks and in-rank order, and change them only as rules 2.4 to 2.21 say, honoured hints (rule 2.21) first (rules 2.2 and 2.3 are pointers).

2.2 See rule 2.18.

2.3 See rule 2.17.

2.4 Put a node with several parents under its first parent that has no other child directly below it, taking parents in Mermaid's order. If every parent has one, keep the node's snapped column (1.6). Inside a 2.10 block, 2.10 decides which source a target sits under.

2.5 If a node has several children, the main-path child (2.18), or off the main path the longest-path child (the child with the longest path to a terminal node), prefers the cell region directly below it with overlapping columns; among equal-fault candidates whose scores tie, choose that region, otherwise the nearest free region by Manhattan cell distance, ties by 9.4. Place remaining children by 2.17, subject to clearance and honoured hints.

2.6 Put detours in the column next to the main path, in the ranks between the two main-path nodes they join. Put early exits in the column beyond the detours. Put both on the side of the main path where Mermaid placed most of them; on a tie, use the left side. A second branch from the same diamond goes on the opposite side.

2.7 When a diamond has two children, one on the main path and one starting a loop branch, keep the main-path child directly under the diamond (rule 2.18) and put the loop child in the next column, one rank lower, on the side Mermaid placed it. Prefer a straight main-path connection only when the allocated symmetric ports align; otherwise use the fewest legal corners (see wait-loop-markup.png, cycle-grid-markup.png).

2.8 A chain of nodes that each have one parent and one child stays in one column as it passes into and out of a group (see nested-chain-markup.png).

2.9 See rule 2.10 (two-by-two is one case of it).

2.10 Block of lines between adjacent ranks (any number of sources and targets). Swap nodes within a rank when that improves the score without breaking higher-priority placement or hints. Order targets by the source supplying the most lines (tie: the mean of the sources' representative columns, where a source occupying columns A to B has representative column (A + B)/2, using rows instead in left-right diagrams; these are ordering values only and never set placement or allow fractional occupancy; then Mermaid order). Prefer a straight connection when the **allocated symmetric ports actually align**; otherwise route with the fewest legal corners. Every other line leaves and enters at ports allocated jointly and symmetrically (3.2, 3.3). Use separate overlapping tracks (5.1), remove avoidable crossings (5.9), and allow only right-angle crossings inside gaps. Do not introduce hops, side detours or frame-edge runs. Grow gaps only for legality (1.7).

2.11 Compaction (`grid` only). After initial placement and routing, visit nodes in rank order, then left to right. Consider moving an unhinted node by whole cells, keeping its spans, to a nearer legal position, including beside a parent when 2.17 permits it. **Never move a main-path node sideways for compaction**; a deliberate wrap fold (2.12) is the sole automatic exception. Retain a move only when the complete candidate satisfies the applicable rules and has a strictly lower score (2.13). After a move, reroute affected connections under 4.2. Move clusters as units unless an honoured hint requires a different arrangement (2.20–2.21); group membership and frame containment remain governed by 7.8. Remove only genuinely unused rows/columns; never shrink a gap needed for labels, tracks, corners or frames. Repeat until rule 2.14 stops the search. Hard: compaction never splits, shrinks, collapses or enters a spanning node's region and never produces a fractional size; main-path and hint restrictions still apply.

2.12 Wrapping (`grid` only). After compaction, wrap rows or columns only when the measured span along the flow axis would exceed `diagram_usable_width_px` (548 px at default embed). There is no fixed diagram-size or node-count limit beyond that page width. Preserve source order and honoured hints. A long main path **may fold only at an explicit wrap boundary**: each uninterrupted section remains aligned, and the connecting edge is routed under sections 3–5. The fold is not an ordinary sideways compaction move. Layout must never stretch or add space to chase a target shape. Run compaction after wrapping and keep only strictly improving candidates (2.14). Tests compute expected dimensions from measured node sizes and gaps and never hard-code pixel dimensions. Hard: wrapping never splits a node across rows or columns, and never splits a group frame unless the group itself exceeds the wrap length.

- The wrap length is the maximum number of cells across, or down, that keeps the wrapped segment within `diagram_usable_width_px`. Never wrap a row or column that already fits within that span.

- Wide: cut a row longer than the wrap length into rows of at most that length. Draw the first nodes across, then start the next row directly under the previous row, in the same columns, one rank gap below.

- Deep: cut a column longer than the wrap length into columns of at most that length. Draw the first nodes down, then start the next column directly to the right of the previous column, one column gap away.

- Keep the order of the nodes: the next row or column continues from the node after the last one in the previous row or column.

- One line joins the pieces. For a wrapped row, it leaves the bottom of the far-right node, runs back along a track in the gap, and enters the top of the first node of the next row. For a wrapped column, it leaves the right side of the bottom node, runs along a track in the gap, and enters the left side of the first node of the next column. This line follows sections 3 to 5 like any other line.

- After wrapping, run compaction (rule 2.11) again, so that wrapped rows and columns pack closer. A diagram can need both wide and deep wrapping. Compaction and wrapping repeat in passes; candidates are scored and kept, and the loop stops, as set by rules 2.13 and 2.14.

- The wrap length is counted in base cells (rule 1.3); a node that spans several columns or rows counts its full span. Tests compute the expected size from measured node sizes and the gaps, and never hard-code a pixel size or a node limit.

2.13 Layout score. Score each **legal, routing-fault-free (unless hinted)** candidate of the same diagram: shape + empty + crossings + bends + disconnected ends + hints; lower is better. Shape: 2 points per 5% deviation from 4:3, prorated; this is a small cost, never an admission condition or a hard limit. Empty: 10 points per 5% uncovered area through 30%, then 40 per 5% above 30%, prorated; measure against node boxes, group frame/title space, labels and occupied tracks. Crossings: 20 points per crossing **above a defensible forced minimum**, prorated only where meaningful. The forced minimum is the minimum under the permitted node/port/track orderings; do not assume a closed-form complete-bipartite formula applies to unrestricted orthogonal routing. Where it cannot be established, use zero as a conservative lower bound. Crossings up to that minimum are reported but unpenalised. Bends: 20 points per corner. Disconnected ends: 20 per unmatched drawn line end (but such ends are prohibited by section 10, so legal candidates normally have zero). Hints: -30 per independently honoured placement-axis hint of an element, note or group, and -15 per fully honoured connection-level line hint, including plain note connections (2.21). Tests calculate expected scores from the measured layout and never hard-code a pixel size. The score cannot legalise a forbidden crossing, routing fault or overlap; it is not a pass mark. Read all weights from this rules file. Score from final rendered sizes. Gaps inside a node's region count as occupied area, not empty space. A node that spans more than one cell earns no penalty for its span. Length. Add one bounded route-length term to each complete legal candidate. Let L be the total final route length divided by the base routing grid unit, w be score_route_length_per_grid_step, and B be the smaller of score_bend and score_crossing. The length term is wL / (1 + wL/B). Add it once for the whole layout, not once per line. It is nonnegative and strictly less than B for every finite route length, so length alone cannot outweigh one bend or crossing. Measure complete terminal runs as well as interior tracks. Compare length exactly when the bend-and-crossing costs tie; a fixed score epsilon must not discard a real length improvement. Hints and all legality and routing-fault admission checks remain higher priority. The existing route-length and moved-line repair score terms under 5.10 remain separate. Added route length and bends are priced in the score, without added-length or added-bend caps.

2.14 Keep the best. Compare complete candidates in the fault-first order of 9.1 (legality faults, honoured hints, non-exempt routing faults, then score); among candidates equal on the first three, accept only a strictly lower score. Stop after a full pass without improvement or a repeated layout signature. A finite deterministic candidate enumeration and a visited-layout set prevent cycles; do not impose an arbitrary diagram-size limit. Report any independently unsatisfiable hard constraint rather than expanding indefinitely (1.7). Empty space above 30% is a reported quality result, not a conversion failure. A candidate's state and layout signature include every node's start row, start column, row span and column span.

2.15 Unconnected pieces. Arrange disconnected nodes or connected pieces in declared order, left-to-right then top-to-bottom. Compute the block’s own wrap length from its measured member dimensions and spacing so each row or column fits within `diagram_usable_width_px`; do not depend on the whole-diagram wrap length (2.12). A cluster is initially one piece. Hard: every member stays within its owning group (7.8), whose frame grows to fit.

2.16 Fans. Arrange fan members into a local block whose wrap length is chosen from the fan block’s own measured dimensions and gaps so the block fits within `diagram_usable_width_px`; do not depend on the overall diagram wrap length. Where permitted, place the source or target beside the block, in the rows (or columns) the block occupies, balanced so that the number of block cells on either side of it differs by at most one (a quality preference); when that is not legal, use the most balanced legal position. This specific rule overrides generic 2.17 placement, subject to hints and legality. Route fan lines by 5.2 and 5.8, including nested tracks. Crossings follow 5.9; hops are forbidden (section 10). Fan members may have different spans; never require equal sizes.

2.17 Under the parent. Prefer to place a child in the rows directly below its parent, with its columns inside or overlapping the parent's columns, when its allocated ports permit a legal route. Where the spans allow and scores tie, choose the position whose columns sit evenly within the parent's columns, for example a 2-column child in the middle 2 columns of a 4-column parent; this is a tie-break after 2.13, not a legality requirement. For multiple children retain symmetric port allocation (3.2) and arrange the children's regions across the columns in port order. If a port away from the middle of its edge and a child directly below would require two corners with insufficient horizontal clearance, move the unhinted child outward by whole columns until the required horizontal and vertical runs fit; adding vertical rank-gap space alone does not fix horizontal clearance. A child may grow in any direction (1.2), and parent and child need not have the same spans; their allocated ports decide whether a straight connection is possible. There is no alignment score; alignment is rewarded only through straight connections and the bend and crossing terms. Never resize a node to fit under its parent. Main-path alignment is preferred but not forced against port geometry. Decisions follow 3.8, fans follow 2.16, and multiple parents follow 2.4. Never assume nodes have equal sizes; compare occupied regions.

2.18 Main path. Select the path by longest decision-free continuation, with Mermaid order breaking ties; convergence follows the strongest incoming flow. Prefer to keep main-path nodes in one run of shared columns: each node's columns overlap those of the node before it so that their allocated ports can align, and the edge between them is straight when they do. At convergence, place the rejoining node in the rows below the main-path node feeding it, with overlapping columns, when legal; otherwise use the nearest free cell region and 4.11. Reserve the actual outline port for a legal straight main-path edge before symmetric allocation of the other ports. Reposition unhinted children by whole columns to make routes from ports away from the middle of an edge legal (2.17). Neither compaction nor coupled repair may move a main-path node sideways; only an explicit wrap fold (2.12) or honoured hint may do so. A node that rejoins remains on the main path.

2.19 Free direction. When a diagram declares no direction, the engine tries each flow direction (down, right, up, left) and keeps the layout with the lowest score (rules 2.13 and 2.14), so a simple chain comes out as a straight run with the fewest corners. Hard: when a direction is declared, it is used and not changed. Hints (rule 2.21) apply inside the direction in use and never change a declared direction; with none declared, each trial scores its own honoured hints. Preference: there is no size threshold: the same rule applies to small and large diagrams. Each trial applies rule 1.1 to its direction, and Mermaid's ranks are recomputed for it. Trials may run in parallel and reuse results.

2.20 Clusters. Identify clusters from relationship connectivity only, never labels. Nodes belong to at most one cluster, and otherwise form single-node clusters. Hard: a cluster does not cross a group frame. Preference: move and wrap clusters as units **unless an honoured hint requires a different legal arrangement**; hints outrank clustering and must not be refused merely because they distort or split an automatic cluster. If needed, dissolve or recompute the affected cluster around the honoured hint while preserving group membership and geometry. Choose internal order to minimise crossings under higher-priority rules. Between clusters use 2.10. Cluster detection must have a deterministic tie-break based on source order. Hard: a cluster reserves its members' full occupied regions and moves them intact.

2.21 Hints. Hints override automatic placement and routing, but never hard legality. An honoured line hint may explicitly permit the routing fault it identifies. An honoured node or group placement hint can make a routing fault (precedence level 3, 9.1) unavoidable; keep the hint, report and score that fault under 2.13 rather than dropping the hint to remove the fault. A placement hint never permits a section 10 legality fault. Hints outrank automatic clusters, compaction, wrapping and main-path preferences. Resolve contradictory hints in source order (d). Report impossible hints alongside the fallback diagram.

- (a) Written: a node, note or group hint is written after its declaration's label, before or after its `in` clause. Horizontal hints are left-of or right-of a named peer, optionally followed by +n, or push E or W. Vertical hints are above or below a named peer, optionally followed by +n, or push N or S. A declaration carries at most one effective hint on each axis. A further hint on an axis that already has one is dropped and reported, and hints on one axis are never combined. A line hint is written in square brackets after the relationship: leave, enter or travel, each followed by N, S, E or W, separated by commas. Every direction word is relative to the reader's view of the finished page, whatever the diagram direction (rule 1.1).

- (b) Meaning: a relative hint is a relationship to its peer's complete final occupied region, not a stored cell. In zero-based logical cells: right-of P +n gives StartColumn = P.StartColumn + P.ColumnSpan + n; left-of P +n gives StartColumn = P.StartColumn - Node.ColumnSpan - n; below P +n gives StartRow = P.StartRow + P.RowSpan + n; above P +n gives StartRow = P.StartRow - Node.RowSpan - n. The standard column gap or rank gap between the two regions is always kept. Recalculate the position whenever the peer moves or the relevant span of either node changes. The hinted node's whole region must be free, and the final layout never contains an overlap. A node with a hint on one axis only takes its peer's start row (or column) on the other axis. If its region is occupied, it moves further in the hinted direction by whole cells and never changes that start row or column. A node with hints on both axes has both start coordinates fixed by its relationships. "push D" places the node just beyond, in direction D, the occupied envelope of its reference set: every sibling (same parent) without a push hint, plus every sibling whose push hint comes earlier in source order. The node itself and later-pushed siblings are excluded. The node keeps its coordinate on the other axis. A push may enlarge the group or diagram, and successive pushes stack outward in source order. A later push never invalidates an earlier honoured push. Re-evaluating with unchanged reference regions must not move the node. When reference regions grow or move, recalculate in source order. With an empty reference set, drop the hint and report "no sibling reference region". "leave D" and "enter D" name the side of the source box and of the target box that the line uses. "travel D" is the direction of the line's middle run, so a straight line, which has no middle run, cannot honour travel.

- (c) Peers: a peer must be an element, note or group at the same nesting level in the same group. A missing or cross-group peer causes the hint to be dropped and reported. Peer circles are detected separately on each axis. A valid peer may belong to another automatic cluster: honour the hint first, then move, split or recompute clusters without breaking group membership or geometry.

- (d) Order and conflicts: take hints in source order. A hint that closes a circle of peers on its axis is dropped and reported, and the earlier hints stay. For line hints, two lines hinted to the same port on one box side is a conflict, and the later hint is dropped and reported. Within one line hint, each invalid or repeated part is dropped and reported, the first of a repeated part is kept, and the valid parts stay. Hints may request overlapping occupancy, but the final layout must never contain an overlap. Resolve occupancy with the deterministic legal-repair process, which includes moving whole dependency chains. A neighbour may move only if every higher-priority constraint still holds, including its own honoured hints. An honoured node never leaves either of its hint relationships unless that hint is explicitly dropped and reported. Drop the later axis of a node in source order only after the repair process has used up its permitted candidates, subject to the same higher-priority constraints. Report it as "conflicting constraints" when the conflict is established, and otherwise as "no legal candidate found within the permitted search". Never report a conflict as impossible unless that has been established.

- (e) Hinted nodes retain their peer relation during placement and repairs. Reposition, dissolve or recompute automatic clusters as needed to honour the hint; a cluster is not required to move whole when doing so would break an honoured hint. Group membership (7.8) and hard legality remain binding.

- (f) Legality and routing faults: hints never override legality (section 10); only the marked 5.7 fallback is excepted when no legal route exists. A line hint may expressly permit its named routing fault (precedence level 3, 9.1). A node/group placement hint may make a routing fault unavoidable, but never permits a legality fault: keep the honoured placement hint, report and score the routing fault under 2.13, and do not drop the hint to hide it. Evaluate feasible alternative routes and placements first. Add space when it can honour the hint (1.7); otherwise report the impossible hint and render the deterministic fallback. A valid line hint that forces a detour is honoured, scored under 2.13 and reported with the detour it causes. No cost threshold drops it.

- (g) Score: each placement axis honoured on its own scores -30 in rule 2.13, so a node, note or group with two honoured axes scores -60 and one with a single honoured axis -30. Each honoured line hint scores -15 once per connection, however many parts it has. There is no separate alignment score. The score only compares candidates; it never drops an honoured hint. This is intended: the structure of an original is preferred to calculated layout. A hint that cannot be honoured earns nothing, is reported with the reason, and layout continues; nothing fails.

- (h) Direction: see rule 2.19. A node, group or line without a hint is laid out as before.

2.22 Notes. A note is a free-text dog-ear box, not an Enterprise element or semantic relationship endpoint. Notes may be grouped or top-level, are sized independently from their text; in `grid` mode each note is placed in the smallest whole-cell region that holds its visual bounds, reserves that region, and follows the clearance rules. A connected note sits beside its connected node or group on the same row in the nearest free cell unless an honoured hint moves it; an unconnected note follows 2.15. Group membership and frame containment follow 7.8. Plain note connections have no arrowhead or semantic relationship meaning (4.10); their routes follow 4.2 like every other connection, and they **do not count in the forced-crossing minimum** under 2.13. A line label is not a note.

2.23 Enterprise layers. In enterprise diagrams whose elements come from more than one layer, place the layers as horizontal bands. From top to bottom they are Motivation, Strategy, Business, Application, Technology and Physical (one band), then Implementation and Migration. An element's layer comes from its Enterprise type.

A junction belongs to no layer and sits next to the elements it joins. A location drawn as a node belongs to no layer and sits next to the elements it relates to most. A location drawn as a container is treated like a grouping.

A grouping belongs to no layer and has no position of its own. Its frame is drawn around its members wherever their bands place them. If the members are in more than one band, the frame spans those bands as one solid block, each member stays in its own band, and elements that aren't members are kept out of the frame, even if a band has to wrap.

The bands follow the page. The declared flow direction applies only within a band. Within a band, passive structure goes on the left, behaviour in the middle and active structure on the right. This order applies separately inside each grouping frame's part of the band and among the band's ungrouped elements. Columns are never aligned across different frames, and keeping a frame as one solid block takes priority over the aspect order. A band may wrap onto further rows to approach the overall shape target.

In the Implementation and Migration band, plateaus run from left to right in triggering order, and each gap sits between the plateaus it relates.

A diagram whose elements all come from one layer has no bands.

The band order, band membership and the plateau order are conventions, not preferences. A hint can't put an element in another band, can't move a band above or below a band of a different layer type and can't reorder plateaus. Such a hint is dropped and reported as a warning under 2.26, with no score under 2.21(g). When a declaration has hints on both axes and only one breaks a band rule, only that hint is dropped. A hint can still change an element's position within its own band, the order within the Technology and Physical band, how a band wraps, and where junctions, locations and frames go, as long as every member stays in its own band. Band membership and band order are binding: hints can't override them, and the engine enforces them as a veto.

2.24 Chains stack, branches beside. Preference: place a chain (A to B to C to E) in one column in flow order. Place a side branch (C to D) beside the node it hangs off. Do not scatter a chain across a wide, mostly empty area. This ranks below honoured hints and hard legality.

## 3. Ports and diamonds

3.1 Each line has its own distinct port and non-overlapping first run. A line ends exactly at its allocated port on the node's connection boundary (term Node geometry) and meets that boundary there at a right angle: perpendicular to a rectangular edge or perpendicular to a sloped diamond edge. This requirement applies to diamonds under this rule; a diamond's initial or final edge-normal run is the sole permitted non-horizontal/non-vertical straight run, then turns onto the orthogonal grid after its required minimum length (4.1, 4.4). Diamond ports are allocated symmetrically by 3.2, 3.3 and 4.7. Port assignment and route legality are checked in the layout and routing model, not by an SVG checker. The painter draws only the route supplied by that model; a missing route is reported as an error and is never replaced by a straight centre-to-centre line. Ports are allocated on the node's final connection boundary after its spans are set, never on a one-cell outline that is then stretched.

3.2 Symmetric port allocation. Preference: on each eligible edge of the connection boundary (term Node geometry), allocate jointly. For n lines on an edge, the default slot pattern is k/(n+1), k=1..n; one line uses the edge centre; two use symmetric slots; three use centre plus both symmetric slots; four use four symmetric slots; and so on. A port may leave its slot whenever that removes a bend or makes a rule 4.2 straight run possible. Fewer bends outrank slot symmetry. Adjacent ports on one edge stay at least line_spacing (15 px) apart; that spacing is hard. Preserve target order (3.3) when it does not force extra bends. Port coordinates may be fractional and are not grid-placement coordinates. For rectangular nodes, insufficient spacing calls for a larger span (1.3) or legal port reassignment (1.7). For a diamond, insufficient port spacing or first-run clearance grows that diamond by whole grid steps (1.7). Hinted side choices participate in joint allocation. A line leaves and joins a node at its exact allocated port position, at right angles to the side, and keeps that coordinate until its first bend.

3.3 Port order. Preference: on each connection-boundary segment, order the ports by where each line's other end is, so no two lines cross next to the node. Ordering uses each segment of the final, expanded connection boundary. Port order may give way when reordering removes bends or enables a rule 4.2 straight run; fewer bends outrank strict port order.

3.4 Removed; see 4.8.

3.5 Removed; see 4.8.

3.6 Hard: a diamond's connection boundary is its four sloped edges and four vertices named by compass (N, E, S, W). Sloped edges accept ports allocated under 3.2, 3.3 and 4.7 exactly as box edges do (symmetric k/(n+1) slots where 3.2 applies, aligned straight ports first, adjacent ports at least line_spacing apart). Vertex ports are allowed wherever rule 3.11 names them. One line on an edge uses its centre unless 3.2 reserves an aligned port. Every diamond line enters or leaves perpendicular to its allocated sloped edge for the minimum straight run, then turns onto the horizontal/vertical grid (3.1, 4.1, 4.4). Grow the diamond by whole grid steps under 1.7 if its ports or initial runs do not fit.

3.7 Hard: a diamond branch's perpendicular initial run is at least diamond_min_straight_run (50 px) before turning onto the grid. Preference: for a target directly below, use a downward-facing edge port. Continue by the fewest legal corners; move an unhinted child by whole grid columns if required for corner clearance (2.17). A route is straight only if the required normal departure and target geometry align.

3.8 Decision branches. Hard: allocate each branch a distinct port using 3.2, 3.3, 4.7 and the compass slots in 3.11; each branch departs perpendicular to its sloped edge or vertex normal, runs straight for at least 50 px, then turns onto horizontal or vertical routing (3.1, 4.1, 4.4). Grow the diamond and surrounding gaps by whole grid steps to reduce measured port-spacing or initial-run shortfalls (1.7). Routes are independent and never share a port or first run. Preference: follow 3.11 instead of choosing the sloped edge that faces the branch target.

3.9 Hard: diamond lines use the same symmetric-port, track, corner-limit and crossing rules as other lines, except for their perpendicular-to-edge initial straight run and transition to the orthogonal grid (3.1, 4.1). No line may travel through the diamond interior. Preference: when scores tie, route mirrored destinations as mirror images.

3.10 Arrowhead tips end exactly at the connection boundary (term Node geometry) and never penetrate the node's obstacle geometry. A cross endpoint marker keeps the exterior clearance in parameter cross_endpoint_standoff; its line ends at the marker anchor, outside the box.

3.11 Decision port compass. Hard: compass names are fixed on the diamond (N at the top vertex, E at the right vertex, S at the bottom vertex, W at the left vertex). Inputs: one incoming line uses the N vertex; several incoming lines use N for the centre source, then the NW and NE vertices for the left and right sources, ordered symmetrically. Outputs: the main flow (normal sequence edges and Yes branches) follows S in diagram compass (downward in TB; rule 1.1 maps this for other directions). Match branch labels without regard to letter case, after trimming the surrounding whitespace. The Yes branch is any label equal to Y or Yes (so Y, y, Yes, YES and yes all count), and it leaves at S. The No branch is any label equal to N or No (so N, n, No, NO and no all count), and it leaves at the E vertex only, never at NE or SE, and leads off to the right in TB. When a decision has extra outputs beyond Yes and No, those other branches may still use the SW and SE sloped-edge ports, but No is always E. When three or more outputs leave toward the bottom half-plane without Yes/No labels, use S for the centre branch and the SW and SE vertices for the side branches. A Yes/No decision with one input and two outputs takes its input at N and applies those Yes and No assignments. A line hint may override these preferences only within hard legality. This replaces the edge-facing-the-target preference in 3.6 and 3.8, which now allow vertex ports where 3.11 names them.

## 4. Line shape

4.1 Build ordinary line paths from horizontal/vertical straight runs and 20 px rounded right-angle corners. **Sole exception:** the first straight run leaving, or final straight run entering, a sloped diamond edge is perpendicular to that edge and may be diagonal. After the required minimum straight run, it turns onto the horizontal/vertical grid; that transition is an allowed diamond-edge direction change, not a forbidden diagonal grid run. Do not use arbitrary diagonal detours, S-curves, free curves or hop arcs.

4.2 Hard: allocate ports before routing under 3.2, 3.3 and 4.7, using the relative positions of the two endpoint nodes to determine port order and sides. A connection is a single straight run only when its allocated ports line up and their required departure and arrival directions agree; diamond edge normals are measured against the actual sloped edge (3.1). Preference: always offer the legal straight outline-to-outline route as a candidate, reserving aligned ports before distributing other ports. Straight routing takes priority over symmetric port spacing. If no straight route is legal, compare node or linked-group movement (5.10) and the routes with the fewest legal direction changes from each allocated port (4.8). A legal line hint can override the Preference sentences only. Hard: after any change to a node's spans or position, recalculate its ports, routes, track availability, clearances and crossings, and then the full score (2.13). Preserve exact allocated-port terminal runs and use their drawn geometry for checks under 3.2.

4.3 Hard: a line has at most 2 corners, 3 for a back edge; insert space as rule 1.7 sets until met, and use the rule 5.7 fallback only when no legal repair exists. The sole exception is a line with a hint (rule 2.21), which may use the corners its hint needs (legality.2). A line never loops on itself, and never runs past the side of its target that faces the source and turns back.

4.4 A diamond decision branch travels at least 50 px **perpendicular to its sloped edge** before its first change of direction onto the grid. A line entering a diamond likewise follows the edge normal for its required terminal straight run; its length must accommodate the arrowhead and any transition geometry. Other lines have a port-to-vertex distance of at least min_straight_run (20 px) from their source port before a corner, measured from the port to the corner's vertex (where the centre lines of the two runs meet), so a corner_radius arc may begin at the port, and every arrowheaded line has a terminal straight run at least as long as its arrowhead. Do not impose a universal 50 px source run on ordinary lines.

4.5 Put a Z's middle run on a track in the gap between the source and target ranks (see lr-fanout-markup.png).

4.6 A line never runs along a connection boundary, a visible node outline or a frame edge. It crosses a frame only at a right angle. A line to or from a group follows rule 4.9.

4.7 Port placement. Hard: work out each node edge's centre and slots from the node's drawn outline on the side you can see, not from a bounding box that includes decorations such as a contract shape's top band (the hat). A lone line on a side leaves from the centre of that visible side. Allocate all automatic lines on each eligible connection-boundary segment together under 3.2 and 3.3 (aligned straight ports first, symmetric k/(n+1) slots when bends do not improve the route, adjacent ports at least line_spacing apart). Fewer bends outrank slot symmetry and strict port order. Hard: a legal side hint fixes the chosen side but does not exempt its line from joint port allocation. Reassign affected ports and reroute affected lines together to eliminate avoidable crossings (5.9), preserving hints and distinct connection-boundary ports. Allocate on the expanded connection boundary after spans are set (3.1). Preserve exact allocated-port terminal runs and use their drawn geometry for checks under 3.2.

4.8 Preference: use the fewest legal corners after port allocation: zero only for aligned ports, otherwise one if clear, then a two-corner Z when necessary. Use sides facing the opposite endpoint where the endpoint lies wholly beyond that side; break equal-corner ties in flow direction. Rule 4.11 is the specific convergence exception; 3.8 controls decision branches; 5.3–5.4 control back edges. A line hint may override automatic side and route preferences within hard legality. Hard: do not run through boxes or turn back past the facing side of the target. Corner counts are recalculated after any growth or move (4.2).

4.9 Group endpoints. A relationship may name a group as its source or its target. The endpoint is the group's frame. A line to a frame ends on the frame's real edge, never at the title tab's height or short of the frame. Prefer the shortest legal route to the other end, for example straight into the bottom of a node above, not a loop over the top. A frame defines its own connection boundary, normally its frame edges, and the frame is treated as a box in rules 3.1 to 3.3, 4.2, 4.4, 4.7, 4.8, 5.1 to 5.6 and 2.13, and in line hints (rule 2.21): the line leaves or enters the frame on the side that faces the other end, at a port allocated under rules 3.2 and 4.7, square-on to the frame. The line starts or ends on the outer edge of the frame and never begins inside it, except a line between a group and one of its own members, which meets the inner edge of the frame and crosses nothing else needlessly. A line to a group never runs along the frame edge. A frame endpoint that needs more ports or tracks adds room as rule 1.7 sets (legality).

4.10 Plain connection. A plain connection is an undirected line, with no arrowheads and no relationship type, between a note and a node or group, or between two notes. It is drawn like any other line: sections 3 to 5 apply, a group end follows rule 4.9, its corners and crossings are scored by rule 2.13, and it may carry a line hint (rule 2.21). It is not a relationship and never enters the model.

4.11 Convergence. Hard: allocate all target ports jointly (3.2, 4.7). Preference: a source directly above a target uses a straight top entry **only if its allocated source and target ports align**. An offset source uses the fewest-corner legal entry: top when reachable without a prohibited gap traverse, otherwise the side facing the source. Reserve the top-centre port for a legal straight convergence; distribute offset arrivals across the remaining free sides and slots. A converging line never runs along the gap immediately above the target or uses an S-jog into its top unless a legal line hint explicitly allows that routing fault. Within a 2.10 block, follow 2.10 instead. For fan lines covered by 5.8, defer to the hub-side and nesting choices permitted by 5.8.

4.12 After routing, check every line that bends only to reach its port, because its port is offset from the line's approach or sits on a side that doesn't face the line. Look at the node's other lines on the same side, and on the next sides round where a line could legally use a different side. Swap or move their ports when that removes the bend. Keep a change only if it adds no legality or routing fault, keeps distinct ports, port order (3.3), minimum separation and every honoured hint, and either removes a fault or, with equal faults, adds no crossing anywhere, adds no bend to any other line and strictly improves the score (2.14, 9.1). Reroute only the lines affected. Repeat until no swap removes a bend, visiting each node at most once per pass so the search always ends. Hinted lines keep their hinted side and port.

## 5. Tracks and crossings

5.1 Two lines never share a track (term Track): parallel segments of different lines whose extents overlap by more than geometry_tolerance_px must be at least line_spacing (15 px) apart, and every track is at least line_spacing from the outlines bounding its gap. If a gap has fewer free tracks than lines, insert space as set by rule 1.7 (whole steps of track_spacing) and route again. Never enlarge an unrelated node to create track capacity; grow the gap instead. Initial band placement sizes each gap between columns and between bands for the forecast number of lines passing through it, plus corridor_capacity_buffer: reserve ceil(forecast x (1 + corridor_capacity_buffer)) tracks, and at least forecast + 1, when the forecast exceeds one line; reserve exactly one track when it is one line, and none when it is zero; capacity counts only tracks usable under 4.4 (term Track). Gaps covered by a node that spans several columns are never corridors.

5.2 In a fan, the line to the node furthest out takes the outermost track and port, and the line to the nearest node takes the innermost. Apply this to fan-out and fan-in, and to both halves of the fan (see fan-nesting-markup.png). Fans between columns follow rule 5.8.

5.3 A back edge leaves its source's downstream side if that side is free; if not, it leaves the side facing its return track. It enters the middle of the target's side that faces the return track (see loop-back-markup.png).

5.4 Put the return track on the same side of the main path as the back edge's source. If the source is on the main path, use the side with no branches; if that is still tied, use the right side. When several back edges share a side, the longest takes the outermost track.

5.5 Removed; see 2.10.

5.6 Reconsider affected ports, tracks, sides and unhinted node positions together to remove avoidable crossings (5.9) and humps (a run that moves away from its target and then back, where a route without it is legal). Additional corners are allowed within 4.3 unless an applicable hint permits more. Do not move a main-path node sideways during coupled repair; only a wrap fold or honoured hint can change its columns. Recompute all affected routes, apply legality, then hints, then non-exempt routing faults, then score. Remaining unavoidable crossings must be right-angled and inside gaps. Growing an unhinted node by whole cells is a candidate repair for a measured port-capacity or routing shortfall, within 4.3 and the 5.10 search budgets.

5.7 Every input produces a diagram and diagnostics, even when requested geometry cannot be satisfied. For each repair, measure the outstanding geometric shortfall and accept only a change that strictly reduces it; use whole-step gap growth or whole-column child movement as appropriate (1.7). Port assignment and route validation happen in the layout and routing model. The painter draws only model-supplied routes; it never invents a straight centre-to-centre line for a link with no route. A missing route is an error and must be reported. For non-geometric impossibility, stop retrying and draw a deterministic fallback: retain all nodes and group frames without overlap, preserve group membership, draw every original relationship as an explicitly marked fallback connector using the shortest obstacle-avoiding orthogonal path available, and label the affected connectors as routing fallbacks in the diagnostics. A fallback connector may violate normal corner limits or routing preferences, but must not pass through nodes, hide an endpoint or change semantics. If even an obstacle-avoiding connector cannot be constructed, draw a visible dashed unresolved-connection stub at each endpoint and report the pair; never silently drop an edge or the diagram. This rule applies to input that has been read and validated without errors; a syntax or semantic error fails the diagram before layout (2.26).

5.10 Move before detour. For every bent or detoured route, compare the legal options: move an unhinted endpoint or linked group by one or more whole cells, reroute either clashing line, or retain the current legal route. Include moves that straighten several relationships together, and compact empty rows and columns left by an accepted move. Reroutes may chain when one reroute creates another clash; score the whole chain as one option. Choose the option with the lowest overall repair score, counting added route length (5.10 length weight), each bend (2.13) and every line that must be rerouted (5.10 line weight). A move must obey hints (hints win), preserve the grid and group membership, add no legality or routing fault, and lower the score. For an atomic candidate that moves a fan hub and reroutes every declared line in that fan together, repair_chain_lines_fan_hub is the number of lines in that fan. Moving the hub necessarily changes every fan terminal, so the complete fan must be scored and restored as one assignment rather than truncated at the ordinary twelve-line bound. Every other candidate still uses repair_chain_lines (12). This exception permits no unrelated changed lines and does not raise the candidate-move or chain-depth limits. Route options obey named limits for candidate moves, chain depth and lines per chain; those values protect the 10 second per-diagram target and are set from catalogue measurements. If no move qualifies, route around it as normal. Report when a named limit prevents further candidates from being examined. Growing an endpoint by whole cells (1.3) is also a legal option where it resolves a measured port or routing problem; it counts against the same candidate limits.
In the final repair pass only, after placement, fan nesting, routing and every other repair are complete, a candidate may introduce a new finding identity when the complete candidate, fully rerouted and re-checked, lowers the layout score, adds no legality, hard-gate or routing fault, adds no bends or crossings in that scenario, and does not raise that scenario's total finding count. Every earlier pass keeps the rule that no finding identity may increase.

5.8 Fans between columns. When lines fan out from one source to targets that lie wholly beyond its left or right side, or fan in to one target from such sources, each line leaves the side of the source that faces the target and enters the side of the target that faces the source, at spread ports (rules 3.2 and 3.3). Each line has its own track in the gap between the columns, and the tracks are nested as rule 5.2 sets so that the lines do not cross each other. When a fan's lines cannot all nest on the hub's facing side without crossing, lines to leaves beyond the hub's top edge may use its top side and lines to leaves beyond its bottom edge may use its bottom side. Each side group is nested as rule 5.2 sets, so no two lines of the fan cross. This applies to fan-in and fan-out and takes precedence over 4.11 for these fan lines. The far side, box corners and shared tracks remain forbidden. A line hint (rule 2.21) may name the side within hard legality. Fans to the next rank use the bottom and top sides (rules 2.10 and 5.2). Insert space for the tracks as rule 1.7 sets (see pictures/markup-fan-out-bad.png, which shows what is forbidden).

5.9 A crossing is **avoidable** when any candidate the engine generates for the same placement removes it by a legal reassignment of tracks, ports, sides or extra corners permitted by 4.3, without raising the legality-fault or routing-fault count and while preserving hints and sections 3-5, within the 5.10 search budgets (report when a budget stopped the avoidability check). Avoidable crossings are routing faults, counted under 9.1: prefer the alternative. Evaluate affected lines together. Every remaining crossing must be a right-angle crossing inside a gap; it is reported and costs score_crossing above the forced minimum under 2.13. Crossings never outrank legality: a candidate that removes a legality fault is kept even if it adds crossings (9.1). No hops. Preference: when a line between two nodes has a clear outer path, route round the outside, over the top or round the side, instead of through the middle of the diagram across other lines (see also 5.11).

## 6. Labels

6.1 Centre each label on a straight run of its own line, on a white background, with the line broken round it and one label gap on each side (see edge-label-markup.png). The line keeps its own course through the label: it is never bent, jogged or moved sideways to make room for a label, and a label never sits on a corner. If no straight run is long enough, insert space as rules 1.7 and 6.2 set (label room is legality) (see pictures/markup-decision-branches.png, pictures/markup-three-way-decision.png). A connection label may wrap onto several lines, keeping explicit line breaks; the wrapped label is one rectangle, including padding, and every collision check uses that whole rectangle. It sits on one straight run, clear of corners, and the line stays collinear before and after it. Wrapping a label never bends, jogs or re-tracks the line or creates an S-curve.

6.2 Use the longest straight run that holds the label and both label gaps clear of every corner and arrowhead. On a tie, use the run nearer the source. If no run is long enough, grow the gap it crosses by whole grid steps. If more clearance is needed, use the normal gap growth and repair (1.7).

6.3 Centre every node's label horizontally and vertically inside its visible box. Measure the rendered label bounds; neither the text baseline nor an icon changes the centring point. Node labels are wrapped and measured as part of sizing (1.3), never after routing.

## 7. Groups and frames

7.1 Never cover or shorten the title strip. If the title is wider than the members, widen the frame by whole grid steps.

7.2 Members stay on the shared grid. If a frame needs more room, grow the whole rank gap or column gap; never move a member off its grid line.

7.3 Frames never overlap each other or cross a node that is not a member. Frame clearance is measured on the visual bounds of nodes (term Node geometry). When two frames, or a frame and an outside node, sit in neighbouring columns or ranks, grow that gap to the smallest whole number of grid steps that holds each frame's padding plus (n + 1) x line_spacing for the n tracks forecast through the gap, and a track that a line turns onto from a port on a bounding outline lies at least min_straight_run from that outline, and at least corner_radius, plus arrowhead_length_px for an arrowheaded line, from an outline the line turns into (term Track, 4.4, 5.1); this is at least 1 grid step, or 2 when a line runs through it (see frame-overlap-markup.png). Frames contain the full visual bounds of expanded members. Make room by growing frames or gaps, never by resizing an unrelated node.

7.4 Centre a group across its parent group when it is the only group nested in that parent.

7.5 If both ends of a back edge are members of a group, keep its return track inside that group's frame.

7.6 Keep at least one grid step between a frame outline and every member node on all four sides, below the title band. Grow the frame or its surrounding gap in whole grid steps; never move a member out of its whole-cell region. Insets are measured from the member's full occupied region.

7.7 Centre a group's member layout within its frame horizontally and vertically when the group has no placement hint. An honoured hint (rule 2.21) determines the placement and takes precedence.

7.8 Frame membership. A member that conflicts with its frame grows the frame and is never moved out. A non-member that conflicts with a frame is placed outside it once, and no later step, including 2.11 and 5.6, moves it back inside. A member that grows grows its frame; it is never moved out to make room.

## 8. Sequence diagrams

8.1 Leave the same clear space above and below a note as between two consecutive messages. A note never touches a message line, an arrowhead or a label. Set this in the shared row layout, never for one diagram (see sequence-note-markup.png).

## 9. Precedence

9.1 Apply precedence in this order: (1) hard legality (section 10, and the binding band membership and band order of 2.23); (2) honoured hints, subject only to hard legality; (3) fewer non-exempt routing faults (an applicable line hint may expressly permit a fault); (4) score-based optimisation. Mandatory structural constraints are applied during candidate construction; automatic placement preferences yield to hints. Avoidable crossings are routing faults under 5.9. Comparison is fault-first and lexicographic: fewer legality (hard-gate) faults; then more honoured hints; then fewer non-exempt routing faults; then lower score. Crossings and bends count only through the score. Counts compare totals. A repair may change which finding identities are present only in the final repair pass (5.10); whole-layout candidates (placement, direction trials, wrapping, compaction) are compared by counts alone; and no repair may raise the legality-fault or non-exempt routing-fault count. Insert space only for legality or to honour hints. Valid cell occupancy is hard legality and beats every visual preference; no preference for equal node sizes may block growth that legality needs, and no optimisation may allow fractional occupancy or overlap.

- Finding: one reported rule violation, identified by its **finding identity** = rule or section 10 item id plus the ids of the lines, nodes or frames involved.

- Hard gate: a section 10 legality item or a 2.23 band membership/order violation; a hard-gate fault is a finding of one.

- Scenario: one diagram (one test case) laid out end to end; counts and comparisons "in that scenario" cover that diagram only.

9.2 Grow space only to reduce a measured legality or hint-clearance shortfall. If a port offset leaves insufficient horizontal room for corners, move the unhinted child by whole columns (2.17); growing a vertical gap does not fix that defect. When normal geometry is unsatisfiable, use the visible diagnostic fallback (5.7), not an unbounded retry or omitted diagram.

9.3 A specific rule beats a general automatic rule within one step of 9.6: diamond-specific first-run and sizing rules (3.6–3.9, 4.4) add to the shared port rules (3.1–3.3, 4.7) and win where they conflict (edge-normal run, 50 px minimum), while back-edge rules (5.3–5.4) supplement forward-line rules. Hints override all automatic rules except hard legality.

9.4 Evaluate each candidate in the order of 9.1: hard legality, honoured hints, non-exempt routing faults, then complete score (2.13). Specific geometric rules take precedence over general automatic rules, but never over an honoured legal hint. Automatic ties, in order: fewer cells off Mermaid's snapped grid position, fewer main-path nodes whose columns do not overlap the columns of the preceding main-path node, fewer crossings, fewer corners, labels nearer their line's source, then Mermaid source order.

9.5 If a choice is still tied, keep Mermaid's order.

9.6 Execution order. Parse and validate hints; determine direction, main path, decisions, fan/block placement, clusters and disconnected pieces. Apply hints as constraints throughout, ahead of automatic placement. Allocate ports jointly, route decision branches, convergence, fans and back edges, then minimise corners. Check hard legality, honour legal hints, count non-exempt routing faults and only then score candidates (fault-first, 9.1). Apply compaction and wrapping. For each routing fault, apply the bounded move-before-detour repair (5.10) before changing the route; then run coupled repairs and reroute all affected lines. Coupled repairs never move main-path nodes sideways except at an explicit wrap fold or by hint. Repair only measurable shortfalls; if unresolved, render the fallback and diagnostics (5.7). Direction trials select among completed candidates; Mermaid order resolves ties.

## 10. Must never (normal candidates are rejected for these violations; a marked rule 5.7 fallback connector is excepted only when no legal route exists, remains a reported diagnostic, and is never synthesized by the painter from node centres)

- In `grid` mode, a node whose occupied region is not one contiguous rectangle of whole cells, a fractional or zero span, two nodes occupying the same cell, a frame edge off the fine grid, a node move that is not a whole number of cells, or gap growth that is not a whole number of grid steps. Also forbidden: a node whose region skips a cell or consists of separate cells; a spanning node whose rendered rectangle leaves out a gap inside its region; growth that reduces the gap to another node below its minimum; a node using cells reserved by a diamond; and drawing or treating a spanning node as several nodes. Fractional **rendered** port, curve, text and arrowhead coordinates are permitted. In `open` mode, grid-alignment constraints do not apply. Two nodes overlapping, or unequal rank gaps not justified by rule 1.5, are forbidden in either mode.

- A diagonal run **except the single edge-normal initial/final straight run at a sloped diamond edge** (3.1, 4.1), a curve other than an allowed 20 px orthogonal corner or diamond-to-grid direction change, an S-curve, a hop arc, or more corners than 4.3 permits (except a hinted line or a marked fallback connector under 5.7).

- A line whose allocated ports align but is drawn as anything other than one straight run (unless a legal line hint overrides its route), or a source/terminal run shorter than the applicable minimum in rule 4.4.

- A connection that does not end exactly at its allocated port on the node's connection boundary, which is shape-specific and may differ from the visible outline (term Node geometry): a line end short of the port, extending into the node's occupied geometry, attached to an ineligible decorative feature, or on a box corner.

- Two lines sharing a port or first run, or sharing a track: parallel segments of different lines that overlap by more than geometry_tolerance_px and are less than line_spacing (15 px) apart (term Track, 5.1).

- A line intersecting the obstacle geometry of a node it does not connect to, or through a label it does not connect to, or running along a connection boundary, visible node outline or frame edge.

- A line crossing a frame other than square-on, or a crossing of two orthogonal line runs other than at a right angle within a gap. Avoidable crossings are governed separately by the routing-faults list and rule 5.9.

- A line running past the target’s facing side and turning back, or a diamond line crossing its own diamond interior. Diamond branches may leave from any allocated edge port.

- Frames overlapping, a frame crossing a non-member node, a member placed outside its owning frame, or a title strip covered or cut short.

- A label touching a line, arrowhead, corner, outline, frame or another label, measured on its whole wrapped rectangle; node or connection label text that is clipped, truncated, shrunk or overlapping.

- A sequence note touching a message line, arrowhead or label.

## Routing faults (precedence level 3 under 9.1, below hard legality and honoured hints: a candidate with a non-exempt routing fault loses to any candidate with fewer; an applicable line hint may expressly permit one, or an honoured node/group hint may make it unavoidable under 2.21)

- A line bent, jogged or displaced solely for a label (6.1); a convergence line travelling along the gap above its target or S-jogging into its top (4.11); a fan line using the far side or going around its source, or sharing an overlapping track (5.8); any crossing removable by a legal reassignment or permitted extra corner (5.9). Reject these unless an applicable hint permits the fault under 2.21. The section 10 hard constraints still apply to normal connectors.

## Resolved conflicts

1\. Diamond ports: Diamonds have four edges, each accepting any number of symmetric k/(n+1) ports; one line on an edge uses its centre. Every line meets the sloped outline square to its edge and follows the edge normal for the minimum straight run before turning onto the horizontal/vertical grid (3.1, 3.6–3.9, 4.1). Diamonds grow by whole grid steps when necessary (1.7). No limit applies to outgoing branches.

2\. Elbow or Z: B3 and brief section 8 took an elbow first; B14, A14 and A16 took a Z first. Superseded by rule 4.8: fewest corners, a Z only when no one-corner route is clear (3.4 removed).

3\. Side exits: B5, B11 and A14 disagreed on side exits. Superseded by rule 4.8: a line uses the side that faces the other end when that end lies wholly beyond it (3.5 removed).

4\. Corner limit: B3 set 2 corners for every line, but the back edges in B17 and A13 need 3. Forward lines have 2 and back edges 3 (4.3).

5\. Rearranging: A1 and brief sections 1 and 9 keep Mermaid's rank and order; A5, A12, A13, A14 and A16 change them. The later rules win, and Mermaid's arrangement is the starting point and the last tie-break (2.1, 9.4).

6\. Sides and paths: brief sections 6 and 8 follow Mermaid's sides and paths; the rules here replace them.

7\. Crossings: B8 banned all crossings; A14, A16 and brief section 8 allow one when nothing removes it. Kept the later rule: a swap that removes a crossing is used (5.6, 5.9); the rest are scored (2.13).

8\. Track spacing: brief sections 3 and 7 set 5 tracks 6 px apart; the later A16 set 1 grid step. Superseded on 20 Oct 2026 by line_spacing = 15 px between adjacent lines and tracks; track_spacing remains only the gap-sizing step.

9\. Straight-line port: two lines on one side are spaced k/(n+1), and a single line keeps the centre port so it stays straight. Kept B6 (3.2).

10\. Spine versus a loop branch: A12 keeps the spine in one column; the later A13 puts a loop child and the spine child on either side. The spine child stays under the diamond and the loop child goes beside it (2.7, 2.18).

11\. A bypass that rejoins: A9 moved the rejoin node up beside the detour; the later A12 keeps it on the spine. Kept A12 (2.6).

12\. Back-edge sides and labels: B15 and B17 described the entry side differently, and B12b and B15 placed labels differently. Replaced by one rule each (5.3, 6.2).

13\. Rank gap: brief section 3 sets a 1-step gap. The base rank gap is now 2 grid steps to provide a routing corridor for rounded corners, arrowhead clearance and separate tracks, rather than to impose a universal 50 px source run.

2.25 Keep related nodes close. Preference: a node whose only lines go to one nearby node sits next to that node, not at the far edge with a long return line (for example, Lodge by the 21st under No Late Payments). This ranks below honoured hints and hard legality.

2.26 Diagnostics and error policy. A source that cannot be read as valid statements, or that breaks the model (unknown element type, an invalid relationship type, qualifier or rules-table cell, an unresolved endpoint or container, an unsupported Mermaid arrow or shape, an unclosed block, malformed hint syntax or a duplicate clause), is an error, and the diagram is not drawn. A hint that is read correctly but cannot be honoured, and an invalid or conflicting part of a line hint, is a warning: drop only that hint, axis or part, report it with its reason, and draw the diagram normally. A placement axis dropped by the repair process is reported as "conflicting constraints" only when the conflict is established, and otherwise as "no legal candidate found within the permitted search". A redeclaration that materially changes the effective placement hint is a warning, and an identical one is not. Every diagnostic names the line, the construct and, where one exists, the accepted form. Rule 5.7 applies only to input for which this rule reports no error.

5.11 Use both outer channels. Preference: a line that skips a rank in a single column, or returns up it, leaves from a side port and runs down the outer channel. Lines going up take one side and lines going down the other, so lines never bundle, hop or cross in one gap. A line between neighbouring ranks is a straight vertical.
